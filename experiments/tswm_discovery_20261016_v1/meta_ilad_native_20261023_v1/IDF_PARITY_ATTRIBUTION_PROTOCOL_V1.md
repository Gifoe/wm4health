# Bounded attribution of the IDF native point-metric mismatch

The9-cell CPU recipe is complete and preserved. All18 Meta-iLaD metric comparisons passed the frozen1% reference tolerance;4 of6 IDF comparisons did not. Exact raw/tensor fingerprints, independent metrics and the source input-boundary checks already rule out several dataset/scoring explanations. This protocol is a post-hoc developmental attribution, not held-out method validation or a new benchmark score selection.

Select the largest IDF future-score discrepancy, the shipped s1000 checkpoint, before these controls run. Its source ICEncoder and NoiseEncoder call torch.randn_like once for z0 and twice per each of125 transitions:251 Gaussian arrays. Execute the unchanged source evaluate.py through a wrapper that records these draws. First require CPU torch2.4.1 recording to reproduce the already saved native arrays exactly. A failed wrapper qualification stops attribution.

Five primary cases, all seed1000: A CPU2.4 native draws; B CPU2.8 native draws; C GPU2.8 native draws; D GPU2.8 replaying B's CPU draw bank; E CPU2.8 replaying C's GPU draw bank. Replay still advances the original random generator before substituting a draw; shape/dtype/count must match. One CPU thread and FP32 with TF32 disabled; same source/data/checkpoint. CPU2.4 uses Python3.11/NumPy2.0.1, while2.8 uses the existing CUDA-compatible runtime; A/B is therefore a runtime-bundle check, not a uniquely isolated PyTorch-version effect.

Native B/C contrasts include device-dependent random draws and arithmetic. B/D and C/E hold all251 Gaussian arrays fixed within torch2.8 and isolate the remaining current execution-device effect. Record full-array max/RMS differences and score differences. The random-draw explanation is supported in this local test only if native B/C relative MSE difference exceeds1%, while both common-bank comparisons have relative prediction RMS and relative MSE difference<=1e-3. Otherwise preserve the unresolved/numerical explanation. These thresholds are not changed after outputs.

Two fixed secondary cases run the native GPU2.8 path at the remaining shipped IDF seeds42 and1111, regardless of outcomes. Compare all3 GPU seed metrics with the same1% reference tolerance; do not replace or erase the original CPU results. Total7 additional diagnostic evaluation calls,0 fits. No seed, checkpoint, model or solver parameter is tuned. The vendor reference lacks a complete runtime/noise trace, so even matching GPU numbers does not uniquely reconstruct its external execution history.

[PyTorch reproducibility guidance](https://docs.pytorch.org/docs/2.14/notes/randomness.html) already cautions that equal seeds do not guarantee matching CPU/GPU or cross-release executions. A device/noise explanation would therefore close an ordinary reproducibility issue, not establish a new world-model research gap.
